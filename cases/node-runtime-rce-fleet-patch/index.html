Patching a Node.js RCE across 24 apps in one week

A runtime remote-code-execution flaw left every Node service unfixed. I patched 24 apps and four shared base images in a week, verified against what was running.

By Vitor SchiavoUpdated November 2026~7 min read

Contribution at a glance

My responsibility
The remediation plan, the runtime inventory, base-image and application upgrades, the rollout and its validation, building on a colleague's exposure analysis.
Scope
Two shared Node base images, two PHP base images that bundle Node, and 24 applications across development, staging, sandbox and production.
Collaboration & boundaries
A colleague's analysis identified the affected images and the realistic exposure. Production merges were gated on QA approval. Legacy end-of-life services needing major upgrades were tracked separately and are not claimed.
Outcome
Every in-scope app ran the fixed release in each environment where it ran, and each production deploy was compared with a pre-deploy baseline. This is not a claim of a complete fleet.

A flaw in the runtime, not the code

On 21 October 2026 Node.js shipped fixes for CVE-2026-111497, a remote-code-execution flaw in the Brotli decoder bundled with the runtime. The fixed releases are 22.23.4, 24.22.1 and 26.12.1; Node 20 and older are end-of-life and get no fix. Two days later a colleague's analysis showed that none of our Node services ran a fixed release.

The fleet's Node came from two shared base images. One used a floating Node 22 tag that a monthly rebuild had frozen one patch behind. The other was pinned to end-of-life Node 20 on Debian 10, which meant a major Node upgrade and an operating-system upgrade, not a rebuild. Applications only pick up a new base on their next deploy, so each running service showed its own, older version.

Size the real risk, then plan

The direct attack path over incoming requests needs Express 5 or body-parser 2, and every Express app checked was on Express 4. The realistic exposure was Node code that downloads a response from an attacker. That is lower, but not every outgoing request had been checked, and the product is regulated online safety.

I wrote a four-part plan that week: rebuild the floating base immediately, move the end-of-life base to the fixed release after a per-consumer compatibility check, queue the backlog of end-of-life images and pinned versions, and close the inventory gaps with a runtime check.

Trust the running image, not the repository

The first analysis was repository-based, so it could not say what ran in production. I replaced it with a read-only inventory of every production pod, reading each image's Node version from its digest with crane (distroless images run locally with node -v). It covered 174 container images and found 26 Node workloads: one on a fixed release and 25 vulnerable. It also showed that a service classified as fixable by redeploy never would be, which became the PDF story below.

One gate at a time

I rebuilt the floating base at once, because its tag already resolved to the fixed release, and checked the Debian 12 upgrade of the pinned base against each consumer before merging. The rollout went to development and staging on 26 October, then to production and sandbox on 27 October, one pull request per environment, with production merges gated on QA.

Each service was validated inside its running container (Node version, pods, endpoints, logs, real traffic), and each production deploy was compared with a baseline taken before it: probes, error logs against the previous version, restarts and, where available, Grafana panels. The comparisons found no errors attributable to the upgrade. Two operational hiccups, a liveness restart on a sandbox cold start and a CI agent that ran out of disk, were recorded and handled.

What broke before production did

The Debian upgrade broke three things in development and staging, all fixed before production: the ORM lost its OpenSSL library, a Dockerfile COPY into the root collided with the /lib symlink, and a slow boot outran the probe delay. A distroless worker kept shipping a vulnerable Node even on the vendor's Node 22 tag, so I rebuilt its runtime from the distroless Debian 12 base plus the exact patched Node binary, keeping it shell-less and non-root. One Dockerfile ignored its lockfile because of a misspelled flag, which let a type-package release break a build; the upgrade fixed that too.

The service a redeploy could not patch

A PDF-rendering service kept reporting the vulnerable Node after every rebuild: its runtime stage inherited Node from a pinned vendor Puppeteer image. The obvious fix, bumping that image, would not have worked. Image metadata and the Node security release showed that even the vendor's newest image shipped an unpatched Node 24.21.0, fixed only from 24.22.1, so the version string would have changed while the flaw stayed.

Instead I rebuilt the runtime on the official patched Node image and reproduced what the vendor image provided (runtime libraries, fonts, the same Chrome for Testing version at the same path), keeping Puppeteer unchanged so no application code changed. I validated the artifact, not the HTTP status: a 20-scenario end-to-end suite passed 20 of 20 locally and again against the real development and staging environments, and PDFs in six locales were text-identical to the old image with zero pixel difference across 12 pages. The image also shrank from about 793 MB to about 345 MB. Production promotion was gated on QA sign-off and is outside what this page claims.

Results and what is not claimed

The closing record lists 24 applications and four shared base images on the fixed release in every environment where they ran. Several services with no real traffic were retired, with backups kept, instead of being patched.

This is not a claim of a complete fleet: legacy end-of-life services that need major-version upgrades were tracked as separate work, and the production promotion of the PDF service followed its own gate. Production health is claimed only through the post-deploy comparisons described above.

The lesson

A rebuild is not a patch until the running image says so. Read versions from what runs, check the advisory before taking the obvious fix, and compare every deploy with a baseline.

Decisions and next steps

A retrospective view of the approach and its limits. The next improvement is a proposal, not a delivered result.

Alternative and rationale

Waiting for the monthly rebuild, or bumping the vendor image alone, would have changed version strings without removing the flaw for the services that mattered. Reading versions from running images exposed that.

Trade-off

A runtime inventory and per-deploy baselines cost more than a repository scan and a green pipeline, but they are the only evidence that answers the audit question: what was actually running?

What I would improve next

Next improvement: a scheduled job that compares running image versions with published advisories and opens a ticket, so the inventory stops being a one-off.
