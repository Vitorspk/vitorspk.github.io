Patching a Node.js RCE across 24 apps in one week

A runtime remote-code-execution flaw affected every Node service. I patched the apps and shared base images in a week, verified against what was actually running.

By Vitor SchiavoUpdated November 2026~5 min read

Contribution at a glance

My responsibility
The remediation plan, the runtime inventory, base-image and application upgrades, the rollout and its validation, building on a colleague's exposure analysis.
Scope
The shared base images and 24 applications, across pre-production and production environments.
Collaboration & boundaries
A colleague's analysis identified the affected images and the realistic exposure. Production merges were gated on QA approval.
Outcome
Every in-scope app ran the fixed release in each environment where it ran, and each production deploy was compared with a pre-deploy baseline.

A flaw in the runtime, not the code

On 21 October 2026 Node.js shipped fixes for CVE-2026-111497, a remote-code-execution flaw in the Brotli decoder bundled with the runtime. The fixed releases are 22.23.4, 24.22.1 and 26.12.1. Two days later a colleague's analysis mapped which of our services needed the change.

Node reached our services through a few shared base images. A floating tag can lag a release, and a pinned base can turn a rebuild into a larger upgrade. Applications only pick up a new base on their next deploy, so running services can differ from the base they were built on.

Size the real risk, then plan

I assessed which attack paths applied to our services and how realistic the exposure was, then wrote a three-part plan: rebuild floating bases at once, move pinned bases to the fixed release after a per-consumer compatibility check, and close the inventory gaps with a runtime check.

Trust the running image, not the repository

The first analysis was repository-based, so it could not say what ran in production. I replaced it with a read-only inventory of every production pod, reading each image's Node version from its digest. It covered every running container image, and it showed that a service classified as fixable by a redeploy never would be, which became the PDF story below.

One gate at a time

I rebuilt the floating base at once, because its tag already resolved to the fixed release, and checked the base-OS upgrade of the pinned base against each consumer before merging. The rollout went to pre-production on 26 October and to production on 27 October, one pull request per environment, with production merges gated on QA.

Each service was validated inside its running container (runtime version, pods, endpoints, logs, real traffic), and each production deploy was compared with a baseline taken before it: probes, error logs against the previous version, restarts and, where available, dashboards. The comparisons found no errors attributable to the upgrade, and the two minor operational hiccups along the way were recorded and handled.

What broke before production did

The base-OS upgrade broke three things in pre-production, all fixed before production: a native library the data layer needs was missing, a file-layout collision appeared in the image build, and a slow boot outran the health-probe delay. A shell-less runtime image could not be fixed by moving to a newer vendor tag, so I rebuilt its runtime from a minimal base plus the exact patched binary, keeping it shell-less and non-root. One build ignored its lockfile because of a misspelled flag; the upgrade fixed that too.

The service a redeploy could not patch

A PDF-rendering service kept reporting the vulnerable Node after every rebuild: its runtime stage inherited Node from a pinned vendor browser image. The obvious fix, bumping that image, would not have worked. Image metadata and the Node security release showed that bumping the vendor image would not have removed the flaw, so the version string would have changed while the flaw stayed.

Instead I rebuilt the runtime on the official patched Node image and reproduced what the vendor image provided (runtime libraries, fonts, the browser at the same path), keeping the browser library unchanged so no application code changed. I validated the artifact, not the HTTP status: a 20-scenario end-to-end suite passed 20 of 20 locally and again against the real pre-production environments, and PDFs in six locales were text-identical to the old image with zero pixel difference across 12 pages. The image also became less than half the size.

Results

The closing record lists 24 applications and the shared base images on the fixed release in every environment where they ran. Several services with no real traffic were retired, with backups kept, instead of being patched. This page claims only what that record and the post-deploy comparisons show.

The lesson

A rebuild is not a patch until the running image says so. Read versions from what runs, check the advisory before taking the obvious fix, and compare every deploy with a baseline.

Decisions and next steps

A retrospective view of the approach and its limits. The next improvement is a proposal, not a delivered result.

Alternative and rationale

Waiting for the scheduled rebuild, or bumping the vendor image alone, would have changed version strings without removing the flaw for the services that mattered. Reading versions from running images exposed that.

Trade-off

A runtime inventory and per-deploy baselines cost more than a repository scan and a green pipeline, but they are the only evidence that answers the audit question: what was actually running?

What I would improve next

Next improvement: a scheduled job that compares running image versions with published advisories and opens a ticket, so the inventory stops being a one-off.
