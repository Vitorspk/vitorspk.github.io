Patching a PHP runtime RCE on the day it landed

A critical PHP runtime flaw landed. A same-day rebuild would have fixed nothing, so I pinned the patched version and verified every running container.

By Vitor SchiavoUpdated November 2026~5 min read

Contribution at a glance

My responsibility
The impact assessment, patched and pinned base images, a build guard in the applications, the rollout and the final verification scan.
Scope
Three deployed PHP applications and the two shared base images they use; one undeployed repository moved off end-of-life PHP.
Collaboration & boundaries
Development and staging merged straight away; production merges waited for review and approval. Virtual machines and serverless services outside the main projects were not scanned.
Outcome
The closing scan found no vulnerable PHP runtime among 1,603 running containers (511 unique images), on the day of disclosure.

Two flaws in the runtime itself

On 21 October 2026 the PHP project released emergency updates for two critical flaws that let an unauthenticated attacker run code on a web server. They sit in the language runtime, not in application code, so any PHP site is exposed whatever its own code does. The fixed releases are 8.5.12, 8.4.27, 8.3.36 and 8.2.35, and only upgrading fully protects a server.

Read what runs, not what the Dockerfile says

I read PHP_VERSION from each image's config and php -v from the running production pods. Three deployed applications were vulnerable: a demo application, an internal tool and a notification service with three workers. So were both shared base images. A fourth repository, not deployed anywhere, ran end-of-life PHP 8.1, which gets no fix and had to move to 8.3.

Why a rebuild would have patched nothing

Our base images use floating tags. After the release, the registry kept serving the vulnerable version under the floating tag for several hours, so a rebuild right after the announcement would have shipped the same version. A second trap sat in the process: the shared base is rebuilt monthly, but applications only pick it up on their next deploy, so a production service was already two patch versions behind its own base.

Pin, guard and prove the swap is neutral

The fix pins the exact patched version in the base images and Dockerfiles. Before merging, I validated the pinned Dockerfile by building the official image recipe from source, checking the tarball checksum and signature, and confirming that the module list matched the current base exactly. The applications got a build guard that refuses any base below the fixed version, so a stale base can no longer reach production silently.

To show the change was neutral, I compared a control, the old base with the guard lowered, against the patched build: the same PHP modules, the same web-server-to-FPM responses on the checked routes, the same framework version and the same test results, 432 passing with the same 25 pre-existing failures, none related to the runtime.

Rollout order mattered

Development and staging were merged right away; production waited for review and approval. Merge order mattered: merging an application before its base was patched would have made the pipeline fail on the new guard and block every deploy of that application. The base was rebuilt and verified first, then the applications followed.

Proving it on the whole cluster

The closing step scanned every running container in every cluster context: 1,603 containers, 511 unique images, and no vulnerable PHP runtime left. The production services moved from 8.3.33 to 8.3.36, and the demo application to 8.4.27 in all four of its environments. The scan did not cover virtual machines or serverless services outside the main projects, and this page says so rather than claiming universal coverage.

The lesson

Patch what runs and prove it where it runs. A floating tag, a monthly base and a green pipeline can all look patched while serving the old runtime.

Decisions and next steps

A retrospective view of the approach and its limits. The next improvement is a proposal, not a delivered result.

Alternative and rationale

A rebuild on announcement day, relying on the floating tag, would have looked like a fix and shipped the vulnerable release. Pinning the exact version made the outcome deterministic.

Trade-off

Pins need maintenance. The build guard turns silent drift into a loud failure, at the cost of occasionally blocking a deploy until the base is rebuilt.

What I would improve next

Next improvement: scan running containers on a schedule, so the next advisory starts from a current inventory instead of a one-off.
