The lock that vanished: a full Redis and immortal keys

A scheduled job kept losing its lock: a shared production Redis had been full for a month, and keys that never expire had crowded out everything evictable.

By Vitor SchiavoUpdated November 2026~6 min read

Contribution at a glance

My responsibility
Read-only diagnosis, same-day mitigation, alert design, attribution of the non-expiring keys, the TTL fixes and a scripted, authorized clean-up of the backlog.
Scope
One shared production Redis serving many services; TTL guards deployed to six of them.
Collaboration & boundaries
Production steps were approved one at a time. I left the eviction policy alone because some services might use Redis as a store, not just a cache.
Outcome
The job held its lock after the first resize, with memory down from 100% to 58% and evictions at zero. Not every producer or historical key is fixed.

A lock that nothing deleted

A scheduled billing job stopped early three times in one day with a lost-lock error. It holds a Redis lock with a six-hour TTL and refreshes it as it works, and a run stops when the refresh finds the key gone. The first run lasted over two hours; the next two lasted under two minutes. The logs showed no lock loss in the days before, and nothing in the application deletes or flushes that key, so something outside the application was removing it.

Full is normal for a cache. Squeezed is not.

The shared production Redis had been at 100% of its memory for more than a month. Under its default eviction policy, volatile-lru, only keys that carry a TTL can be evicted. Millions of keys had been written without one, about 9.8 million in a single database and growing by roughly 200,000 a month, so they could never leave. They squeezed the evictable keyspace from about 160,000 keys in late September to around 2,000 on the day of the incident, and any new key with a TTL, the lock included, survived only minutes.

The next stage would have been out-of-memory write errors for every service on the instance. Neither existing alert could have fired: one watched the host's memory, which sat steady near 70%, while Redis sat at its own limit.

Mitigate first, diagnose without touching data

I raised the instance from 5 to 8 GB the same day and measured the effect: memory fell from 100% to 58%, evictions dropped from roughly nine thousand every three minutes to zero, and every application pod stayed ready with no restarts. The next billing run held its lock and kept processing in two read-only checks.

Diagnosis stayed read-only: the job's logs, a code review and the instance's own metrics. Looking at the keys themselves needed explicit authorization. I then sampled 400 random keys per database for type, TTL and size, with masked names and no KEYS, SCAN or writes, and grouped them by key pattern. At that sample size each share is accurate to about five percentage points, enough to name the producers.

Alert on the failure, not on fullness

A cache at 100% is normal operation, so paging on fullness would only teach people to ignore the alert. The critical policy watches the number of keys that can still expire: below 100,000 for 30 minutes. A warning fires at 98% memory. Backtested on the incident, the critical policy would have fired five days before the job broke, and both policies carry documentation on the cause and the next steps.

Make the writers set a TTL

The sample traced the non-expiring keys to specific patterns: session stores created without a TTL, OAuth state keys with no default expiry, livestream and moderation markers, and a session library that passed a cookie MaxAge of zero as the Redis TTL, which means never expire.

Retention was set per service with one rule: an explicit positive TTL, capped at 48 hours for ordinary caches (one narrowly scoped coordination marker keeps a longer limit), and a service that refuses to start if the setting is missing, non-positive or over the limit. The fixes went through development and staging first, with the production configuration set before any code was activated. By 9 November, TTL guards had reached production in six services.

Expire the backlog; do not delete it

Fixing the writers stops new leaks but leaves millions of keys behind. I wrote a resumable script that scans each database, classifies keys with an approved per-prefix rule, and rechecks type, absence of TTL and idle time atomically at write time before applying EXPIRE NX with a random 1 to 24 hour jitter. NX never overwrites a TTL a fixed service had set, no DEL is used, the expiry is spread over a day, and PERSIST can undo it.

A dry run came first, and sixteen regression tests ran against the production Redis version and the exact CLI deployed. A local test caught a trap: EXPIRE refreshes a key's LRU idle age. The run paused until its transport waited for CLIENT NO-TOUCH on the same connection, then resumed. Compiling the classifier's rules once instead of per key cut its time from 0.74 s to 0.05 s per 5,000 keys. On 29 October the passes applied at least 7.9 million expirations.

Delete only what was explicitly authorized

On 9 November, with explicit authorization, a separate pass removed about 1.9 million persistent keys that had been idle for more than 30 days, about 213 MiB of key data. Recorded memory use fell from about 2.99 to about 2.67 GiB, net of concurrent traffic. A second pass removed 38,883 counters, 2.67 MiB, attributed by code and metadata review to a constructor defect already fixed in production. Independent read-only checks found no remaining eligible keys at the fixed cutoff.

What this does not claim

Not every historical key is gone and not every producer is fixed: the closing record does not cover one legacy session store that was identified as the largest source. A newly written 48-hour key had not yet been observed in production at closure, although the automated TTL regression tests passed, and alert notification routing was not revalidated. The instance's capacity was raised more than once and the records of its final size differ, so this page reports only the measured effect of the first resize.

The lesson

A full cache is not an incident. A cache whose evictable share has collapsed is. Alert on the quantity that predicts the failure, fix the writers before widening the eviction policy, and prefer reversible, authorized steps when production data is involved.

Decisions and next steps

A retrospective view of the approach and its limits. The next improvement is a proposal, not a delivered result.

Alternative and rationale

Switching to allkeys-lru would have stopped the crowding at once, but any service that uses Redis as a store would silently lose data. I raised capacity, fixed the writers and waited for the owners to confirm what is cache.

Trade-off

Expiry is reversible and gentle but slow: keys stay in memory for up to a day, and, as the local test showed, it can change what LRU considers idle. Deletion frees memory immediately and needs its own authorization and evidence.

What I would improve next

Next improvement: a per-prefix key-count and TTL-coverage dashboard, so growth in any non-expiring prefix is visible in days, not months.
