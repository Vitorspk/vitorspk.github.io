Restoring trust in the QA pipeline

A shared platform failure made passing tests look broken. Restoring the signal came before fixing individual test suites.

By Vitor SchiavoUpdated October 2026~5 min read

The problem

A QA view contained 73 jobs, with 45 showing red. The obvious response was to repair the failing tests one by one. But a build result is only useful if its reporting and execution platform can be trusted.

The investigation found that 40 of those red jobs shared a failure after test execution: an upgraded reporting plugin no longer found its command-line installation. A passing suite could therefore produce a failed build. Some apparently green jobs had not run for a long time, so the status color alone was misleading in both directions.

My contribution

I investigated the shared failure path, compared historical builds to isolate the plugin transition, repaired the reporting configuration and followed the remaining errors down into the agent platform. I treated platform failures and application-test failures as different workstreams, so the team could see which problem it was actually solving.

The decision

Fix the common execution and reporting layer first. Editing dozens of tests while their reporting mechanism was broken would have hidden the effect of each change and created unnecessary work.

Agent investigation exposed additional compatibility problems: the runtime available to non-interactive builds differed from the interactive user environment, browser tooling was incomplete, and the operating-system/container-tooling combination blocked some workloads. Those needed changes at the platform layer, rather than repeated workarounds in individual jobs.

Validation

Agent images were validated on booted virtual machines. A fleet run across 65 jobs checked for regressions, while error categories were tracked separately. That made it possible to confirm that a platform fix worked without pretending every application test had also been repaired.

Results and measurement

The operational record reports the common reporting error falling from 40 occurrences to zero across the view, with the identified runtime/browser/tooling platform errors also eliminated. The 65-job validation run recorded no regressions.

This does not mean all 73 jobs became healthy. Remaining failures included application test defects, expired test accounts and repositories whose delivery path had moved. The outcome was a trustworthy basis for triage, with those remaining responsibilities made explicit.

What I learned

A test dashboard is an observability product for developers. Its freshness and failure semantics deserve the same scrutiny as a production alert. Before optimizing the number of green boxes, establish what each box actually means.
